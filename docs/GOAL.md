# 持续开发目标：做成最好的抖音收藏备份与管理软件

上一个目标（像真实用户一样用、修卡慢难用）已归档到 `docs/goals/2026-11-usability.md`，其中只剩用户真机验收播放体验。

## 目标

抖藏家要让人放心地把抖音上收藏的一切交给它：**存得全、存得住、找得到、看得爽、带得走**。持续开发新功能、打磨现有功能和界面，网页和 iPhone App 一起推进。

- 存得全：收藏、喜欢、合集、关注的作品都能存下来，抖音限流时自己处理，不用人盯。
- 存得住：文件存下后长期完好，丢了、坏了能发现并自动补回；数据库有备份。
- 找得到：搜索、筛选、收藏夹、相册、标签、博主，几秒内找到想看的那条。
- 看得爽：网页和 App 播放器都像抖音一样顺；图集、长视频、横屏都好看。
- 带得走：不被抖藏家锁住，整个存档能被 Infuse / Plex / 文件管理器直接用，能导出。

## 路线图（按优先级，做完一项勾一项，新想法插到合适位置）

### 存得住
- [x] 备份自检：后台慢慢检查每个已存文件还在不在、大小和校验和对不对；丢失或损坏的自动重新下载（损坏的移到 quarantine 不删），网页状态页和 App 下载页显示核对进度、补回数量（9578850、97a1693，TestFlight 第 20 版）
- [x] 自检先快后慢：每分钟清点 2,000 个文件“在不在、大小对不对”（3.5 万个约 20 分钟扫完，之后每天一次），丢失或截断的立即重新下载；校验和照常慢慢算。界面写“全部 N 个文件都在，内容已核对 M 个”（07f16e9，TestFlight 第 21 版）
- [x] 数据库每天自动备份到 data/backups（分片复制不挡写入，每份先 quick_check 能打开，保留最近 7 份，只清理自己做的），网页和 App 设置页显示最近一次并可立即备份（abec3c1，TestFlight 第 22 版）。线上 1 GB 数据库一次 78 秒

### 带得走
- [x] 每个视频旁写一份 Kodi 格式的 .nfo（标题、博主、发布时间、时长、话题、我的标签 / 备注 / 相册 / 收藏夹）和封面：Jellyfin / Emby / Kodi 直接读，Infuse 需打开“本地元数据”开关，Plex 本身不读 NFO（要装第三方插件）。媒体库指向数据目录下的 objects 文件夹即可（3fb0af0）。还没在真的媒体服务器上验收过

- [ ] 相似 / 重复作品识别（同一视频多次收藏或被搬运）
- [ ] 收藏回顾：按年月看收藏了什么、最爱的博主、消失的作品

### 持续
- [ ] 用户真机验收播放体验（只能用户做）
- 每轮巡检线上健康（同步、下载、冷却），发现的问题优先于新功能

## 每一轮怎么做

1. 先看线上健康（容器、同步、下载、冷却日志）；有严重问题先修。
2. 从路线图上往下取一项：先写清楚做到什么程度算完，再写代码和测试。
3. 全部测试通过后提交，推送到 `origin main`（公开仓库，不写个人信息）。
4. 需要上线时用 `~/.config/douzangjia/deploy.sh`（自动备份数据库、留回滚镜像、等同步空闲再切换）。
5. 界面改动要看到真实画面（本机测试后端 + 网页 / 项目模拟器 `Douzangjia QA iPhone 17 Pro`）；App 有改动就发一版 TestFlight。
6. 勾掉路线图，把结果和实测记到进展记录；一轮结束关掉本轮开的模拟器和测试服务器。

## 必须停下来问用户的情况

- 需要用户登录、授权或做真机验收
- 可能删除或覆盖用户数据，或要动 NAS 上的 `.env`、`compose.yaml`
- 提交 App Store 审核或对外公开发布
- 新功能会明显增加对抖音的请求（比如抓评论），可能招来限流
- 设计方向上有两种都说得通的做法、且改动大
- 同一个问题连续两轮没有进展

## 进展记录

- 2026-11-14：目标建立。用户希望做成最好的抖音备份收藏管理软件，持续开发新功能、优化现有功能和界面。盘点：网页已有同步、归档、播放器、相册、标签、备注、全文搜索、消失作品、通知；App 只有首页、作品、下载、消失博主和播放；下载时记了校验和但之后从不检查文件是否还在、是否完好。
- 2026-11-14：做完备份自检并上线。上线后发现严重回归：迁移里给 media_files(status, verified_at) 加的索引让 SQLite 把每个作品“有没有存下的文件”这条高频查询改走新索引，每次扫 3.3 万行，首页、未存统计、续排从几秒变成几分钟，整站卡住约 20 分钟。删掉索引、加了查询计划的防回归测试、自检的读盘改到后台线程并批量写入（97a1693），紧急部署（同步被卡住等不完，备份后直接切换）。恢复后首页约 3 秒、NAS 负载 28→14，自检稳定推进。教训：给大表加索引前要看高频查询的执行计划。另外修好网页测试在 Node 25+ 上全部失败的问题（Node 自带 localStorage 盖住了测试环境的）；新电脑上建了项目模拟器 `Douzangjia QA iPhone 17 Pro`。
- 2026-11-14：巡检线上健康（负载 7–10，首页约 2 秒，半小时存下 244 个）。自检加快速清点并上线，网页和模拟器上看过真实画面；新列不加索引（吸取 022 的教训）。待下一轮确认快速清点扫完全部 3.5 万个文件。
- 2026-11-14：快速清点在上线约半小时后扫完全部 3.7 万个文件，没有丢失或损坏；修了新下载的文件让“全部都在”永远出不来的问题（下载 1 小时内未轮到的不算）。做完数据库每天自动备份并上线，线上第一份 1 GB 备份 78 秒、检查通过；网页和模拟器上看过真实画面。注意：data/backups 里还有 72 份部署前备份共 6.6 GB，从没清理过；NAS 空间充足，暂不动（删除要先问用户）。
